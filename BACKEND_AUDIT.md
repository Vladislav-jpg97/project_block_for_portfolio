# DevTalks Backend Audit

## 1. Исходная архитектура Backend

Backend организован слоями:

`FastAPI routers -> dependencies -> services -> repositories -> SQLAlchemy models -> PostgreSQL`

Pydantic-схемы описывают входные и выходные данные, Alembic управляет схемой
БД, Redis используется для кеширования списков публикаций. Код приложения
находится в `backend/src/backend`; точка входа — `backend.main:app`.

## 2. Используемые технологии

- Python 3.13+
- FastAPI и Pydantic 2
- SQLAlchemy async и asyncpg
- PostgreSQL
- Alembic
- Redis (`redis.asyncio`)
- JWT (`python-jose`)
- Argon2 (`passlib` / `argon2-cffi`)
- Poetry

## 3. Существующие модели

| Модель | Назначение и связи |
|---|---|
| `User` | Учётная запись, email, хеш пароля, bio, karma, активность и роль; публикации, комментарии, голоса и закладки |
| `Post` | Публикация с автором, категорией, Markdown-текстом, статусом, просмотрами и голосами |
| `Category` | Категория публикаций со slug |
| `Tag` | Тег публикаций со счётчиком постов |
| `Comment` | Комментарий с автором, публикацией и самоссылочной связью ответов |
| `PostVote` | Уникальное голосование пользователя за публикацию |
| `Bookmark` | Закладка пользователя |
| `post_tags` | Таблица связи many-to-many публикаций и тегов |

Миксины предоставляют идентификатор, временные метки и slug.

## 4. Существующие API

Все прикладные маршруты, кроме `/` и `/health`, имеют префикс `/api/v1`.
Требование аутентификации указано явно; административные операции доступны
только superuser.

| Метод | Endpoint | Назначение / данные | Доступ |
|---|---|---|---|
| GET | `/` | Проверка запуска | Публичный |
| GET | `/health` | Статус API | Публичный |
| POST | `/api/v1/auth/register` | `UserCreate` → `UserRead` | Публичный |
| POST | `/api/v1/auth/login` | `UserLogin` → access/refresh JWT | Публичный |
| POST | `/api/v1/auth/refresh` | Обновление пары JWT по refresh token | Публичный |
| POST | `/api/v1/auth/change-password` | `ChangePassword` | JWT |
| GET | `/api/v1/feed/` | Пагинированная лента; `feed_type=new\|top\|hot`, `page`, `size` | Публичный, только опубликованное |
| POST | `/api/v1/posts/` | Создание публикации: заголовок, Markdown, категория, до 5 тегов, статус | JWT |
| GET | `/api/v1/posts/` | Список и поиск; `q`, `category_id`, `author_id`, `date_from`, `date_to`, `sort`, `page`, `size` | Публичный, только опубликованное |

| DELETE | `/api/v1/posts/{post_id}` | Удаление публикации | Автор |
| PATCH | `/api/v1/posts/{post_id}/publish` | Публикация черновика | Автор |
| POST / DELETE | `/api/v1/posts/{post_id}/vote` | Добавить / убрать голос | JWT, опубликованная публикация |
| POST / DELETE | `/api/v1/posts/{post_id}/bookmark` | Добавить / убрать закладку | JWT, опубликованная публикация |

| PUT / DELETE | `/api/v1/posts/{post_id}/comments/{comment_id}` | Редактирование / удаление комментария | Автор комментария, JWT |

| GET | `/api/v1/categories/{category_slug}` | Категория | Публичный |
| POST | `/api/v1/categories/` | Создание категории | Superuser |
| PUT / DELETE | `/api/v1/categories/{category_id}` | Изменение / удаление категории | Superuser |
| GET | `/api/v1/tags/` | Страница тегов (`page`, `size`) | Публичный |
| GET | `/api/v1/tags/{tag_id}` | Тег | Публичный |
| POST / DELETE | `/api/v1/tags/`, `/api/v1/tags/{tag_id}` | Управление тегами | Superuser |
| GET | `/api/v1/users/` | Поиск пользователей (`q`, `page`, `size`) | Публичный, краткая схема |

| PATCH | `/api/v1/users/me` | Изменение username, email и bio | JWT |
| POST | `/api/v1/users/me/avatar` | Загрузка JPEG/PNG/WebP аватара (до 5 МБ) | JWT |

через `HTTPException` с 4xx статусом. Повторный email/username регистрации
возвращает 409, неверные учётные данные — 401.

## 5. Найденные проблемы

- Публичный `GET /users/{user_id}` ранее возвращал `UserRead`, включая email.
- Публичная лента, выдача по slug и чтение комментариев не проверяли статус
  публикации — черновики могли быть доступны посторонним.
- Генератор slug вызывался без `await`; выборка тегов использовала неверный
  вызов `scalars`; обновление тегов искало неверное имя поля.
- Кеш Redis не ожидал async `get`, сериализовал ORM-объекты некорректно,
  использовал несовпадающие префиксы ключей и удалял ключи через блокирующий
  `KEYS`; Redis-пул создавался на каждый запрос и не закрывался.
- Создание категории не добавляло её в сессию; сервис тегов не ожидал
  асинхронный список; запрос счётчика тегов ссылался на несуществующий столбец.
- Создание ответа на комментарий записывало `post_id` в `parent_id`; не
  проверялось существование родителя. Отношение автора называлось `autor`,
  а сериализация новых комментариев могла обратиться к ленивой async-связи.
- Снятие голоса проверяло противоположное условие и удаляло `None`; голоса не
  обновляли счётчики публикации корректно. Просмотр публикации увеличивал
  `votes_count` вместо `view_count`.
- `PostBrief.views_count` не совпадал с именем ORM-поля `view_count`;
  частичный PATCH публикации требовал поля, отсутствующие в запросе.
- Публичная схема категории не учитывала nullable `description`; изменение
  названия категории не обновляло slug.
- Валидация смены пароля вручную выбрасывала `ValidationError` вместо
  `ValueError` и сравнивала старый и новый пароль неверным условием.
- `/feed/` был заглушкой, всегда возвращавшей пустой список.
- Реальных тестов не было; каталог `tests` содержал только `__init__.py`.

## 6. Исправленные проблемы

- Публичная выдача пользователя теперь использует `UserBrief` и не раскрывает
  email. Черновики исключены из публичных списков, страниц автора, выдачи по
  slug, голосований, закладок и чтения комментариев.
- Исправлены генерация slug, запрос тегов, полевые имена, атомарное увеличение
  просмотров и редактирование публикаций частичным PATCH.
- Удаление поста каскадно удаляет его комментарии, голоса и закладки вместо
  попытки обнулить обязательный `comments.post_id`.
- Для профиля добавлены загрузка и удаление аватара. Backend проверяет
  содержимое изображения, ограничивает размер и разрешение, хранит только
  пересохранённые WebP-файлы и использует постоянный Docker volume.
- Голоса теперь корректно добавляются и снимаются, синхронизируя счётчик
  публикации и karma автора.
- Исправлены сохранение категорий, обновление slug категории, получение тегов
  и пересчёт `posts_count`.
- Исправлено создание вложенных комментариев; автор загружается до
  сериализации ответа. Дерево комментариев и ответы на новые комментарии
  инициализируют ORM-коллекции без внеплановой асинхронной lazy-загрузки.
- Кеш использует async Redis API, JSON-сериализацию, scan-based удаление
  ключей и общий Redis-клиент, закрываемый в lifespan приложения. Кеш ленты
  сериализуется через response-схему и инвалидируется при изменениях данных.
- Лента теперь работает на существующем API: поддерживает `new`, `top`, `hot`
  и общую пагинацию, не создавая mock-данных.
- `PostBrief` включает текст публикации, чтобы лента, поиск и закладки
  показывали историю так же, как профиль и страница публикации.
- Для аутентифицированного запроса лента и детали публикации возвращают
  реальные `is_bookmarked` и `user_vote`; состояния загружаются пакетно.
- `ChangePassword` корректно отклоняет повторное использование старого пароля.
- Добавлены unit-тесты для кеша, фильтрации черновиков, схемы счётчика,
  частичного PATCH и проверки смены пароля.

## 7. Добавленные функции

- Реальная пагинированная лента с тремя вариантами сортировки.
- Начальные темы публикаций автоматически создаются для новых баз данных.
- Персонализированные состояния голосов и закладок для access token без
  превращения публичной ленты в endpoint, требующий входа.
- Частичное редактирование публикаций и корректный ответ API после записи.
- Короткие текстовые публикации допустимы; пустое содержание отклоняется.
- Валидация существования категории и тегов при создании/изменении публикации.
- Публичный профиль без приватного email.
- Загрузка, замена и удаление аватара владельцем аккаунта.
- Добавлены `backend/.env.example` и инструкции локального запуска в
  `backend/README.md`.

## 9. Безопасность

- Пароли хешируются Argon2, JWT проверяются по настроенному алгоритму и типу.
- Email остаётся только в ответах регистрации и собственного профиля.
- Доступ к публикациям/комментариям черновиков закрыт; изменение и удаление
  публикаций/комментариев проверяют владельца.
- Создание/изменение категорий и тегов ограничено superuser.
- Аватары проверяются декодированием Pillow, ограничиваются по размеру и
  пикселям, преобразуются в WebP с удалением исходных метаданных; имена файлов
  генерируются сервером.
- CORS ограничен локальными origin (`localhost:3000`, `127.0.0.1:3000`,
  `localhost:3001`, `127.0.0.1:3001`,
  `localhost:5173`, `127.0.0.1:5173`); для реального развертывания список
  следует сделать конфигурируемым.
- Найденные до исправления риски: открытый email (MEDIUM) и доступность
  неопубликованных публикаций (HIGH). Исправления внесены; повторно проверены
  response schema публичного профиля и фильтр опубликованных публикаций.
- Refresh-токены не отзываются и могут повторно использоваться до истечения
  срока; ограничения частоты входа и восстановления пароля нет. Перед
  публичным production-развертыванием нужны rate limiting и политика
  отзыва/ротации сессий.

## 10. Производительность

- Публикации загружают автора, категорию и теги через `selectinload`; авторы
  комментариев также загружаются заранее.
- Пагинация ограничивает размер страницы значением 100; сортировка выдачи
  детерминирована по времени и ID.
- Счётчик просмотров увеличивается атомарным SQL UPDATE.
- Кеш-ключи очищаются через Redis SCAN, а не блокирующий KEYS.
- Полнотекстовый поиск, индексы для всех фильтров ленты и нагрузочные тесты не
  реализованы/не проверялись.

## 11. Что осталось нереализованным

Backend сейчас поддерживает публикации, категории, теги, пользователей,
голоса, закладки и комментарии. В коде нет API и моделей для подписок/друзей,
уведомлений, личных сообщений, изображений/загрузки файлов и репостов.
Восстановление пароля также не реализовано. Персонализированные поля
публикаций доступны при наличии access token. Функции не имитировались
фиктивными ответами.

## 12. Готовность Backend к подключению Frontend

Готов для подключения к существующим сценариям регистрации/входа, чтения и
поиска опубликованных публикаций, создания и редактирования публикаций,
голосований, закладок, комментариев, категорий, тегов и базовых профилей.
Для локального frontend origin `http://localhost:3000` уже разрешён CORS.
Перед запуском локально необходимо поднять PostgreSQL и Redis и настроить
`backend/.env`; Docker Compose из корня проекта автоматизирует этот запуск.
Из-за отсутствия `httpx2` проверка через FastAPI `TestClient` не выполнилась.
Docker smoke test подтвердил готовность PostgreSQL и Redis, применение
миграций, успешный `/health`, открытие frontend и получение данных ленты;
полные сценарии регистрации и CRUD не запускались.
